# AI Style Companion — Mentor Tip

## What it does

On the Companion page, alongside the existing rule-based outfit score and recommendations, there's a **Mentor Tip** card: a short, specific styling tip generated by a real LLM call, explaining *why* something works (color theory, silhouette, proportion) rather than just praising the outfit generically.

It reads the actual items on the canvas/look — brand, category, colors — plus the user's selected mood, weather, and skin tone context, and asks the model for 2-3 sentences of concrete, teachable advice.

This replaces what was previously a fully fake/hardcoded "AI" response with a genuine call to an LLM.

## How it's built

### Request flow

1. The Companion page (`artifacts/styleverse/src/pages/companion.tsx`) resolves which look is being reviewed — either a saved look (`?lookId=`) or an unsaved draft passed straight from the Canvas (`?items=<id,id,...>`), which takes priority so "Ask Companion" works without forcing a save first.
2. On load, it fires a `POST /api/companion/mentor-tip` with the resolved items (name, brand, category, colors, occasion tags) plus mood/weather/skin tone, and tracks `mentorTipLoading` / `mentorTipError` / `mentorTip` state for the card.
3. The backend route (`artifacts/api-server/src/routes/companion.ts`) builds a single prompt describing the outfit and context, and calls OpenRouter's chat completions endpoint directly with native `fetch` — no SDK, no queue, just one request/response.
4. The model's reply is returned as `{ tip: string }` and rendered directly in the gradient "Mentor Tip" card.

### Why OpenRouter, and why a fallback chain of models

The route reads `OPENROUTER_API_KEY` from the environment (see [Secrets](#secrets) below) and calls `https://openrouter.ai/api/v1/chat/completions`.

A single hardcoded free-tier model turned out not to be reliable enough to ship with: OpenRouter's free tier gets rate-limited unpredictably, and *which* model is throttled changes from day to day (verified repeatedly by direct testing — a model that worked one day 429'd the next, and vice versa). So instead of one model, `MENTOR_TIP_MODELS` is an ordered list tried in sequence:

```
const MENTOR_TIP_MODELS = [
  "tencent/hy3:free",
  "openai/gpt-oss-20b:free",
  "nvidia/nemotron-3-nano-30b-a3b:free",
  "google/gemma-4-26b-a4b-it:free",
  "meta-llama/llama-3.3-70b-instruct:free",
];
```

The route loops through this list, moving to the next model on *any* failure — a 429, any other non-OK HTTP status, or an empty completion — and only returns an error once every model in the list has failed. Failure reasons are collected and included in the response body's `details` field for debugging, but the user-facing `error` message stays generic and actionable ("please tap Retry in a moment") rather than surfacing raw provider errors.

This list was built empirically the same way the original single model was: querying OpenRouter's live `/api/v1/models` endpoint for what's currently offered free, then directly testing each candidate rather than guessing model names or trusting that a previously-working model still exists (OpenRouter regularly retires free-tier slugs entirely, returning a 404 pointing at the paid equivalent — several previously-considered candidates like `meta-llama/llama-3.1-8b-instruct:free` and `deepseek/deepseek-r1-0528:free` no longer exist as free models at all).

### Why a hand-rolled route

The rest of the API surface (products, hubs, challenges) is generated from `lib/api-spec/openapi.yaml` via Orval into typed Zod schemas and React Query hooks. This route deliberately skips that pipeline, matching the precedent already set by the voting feature: it's a simple, fast-moving integration where a proxied `fetch` call is enough, and running it through full OpenAPI codegen would add ceremony without real benefit.

### Error handling and retry

The route returns distinct failure modes so the frontend can show a useful message instead of a silent blank card:
- `500` if `OPENROUTER_API_KEY` isn't set at all.
- `400` if the request has no items.
- `503` only once every model in `MENTOR_TIP_MODELS` has failed, with a friendly "please tap Retry" message rather than a raw provider error dump.

On the frontend (`companion.tsx`), the Mentor Tip card shows a **Retry** button on failure. This isn't just cosmetic — the initial fetch is triggered by a `useEffect` keyed on the outfit/mood/weather/skin-tone, so without an explicit retry mechanism, clicking the page's general "Re-Analyze" button wouldn't actually re-trigger the tip fetch unless one of those specific values had changed. Retry works by bumping a dedicated `mentorTipRetryToken` counter that's also in the effect's dependency array, forcing a fresh fetch regardless of whether anything else changed.

### Secrets

`OPENROUTER_API_KEY` lives in a local, gitignored `.env` file (see `.env.example` at the repo root) that `run.sh` reads and passes through as an environment variable when starting the api-server — it is never committed to the repo or written into any tracked file. Anyone cloning the repo needs to supply their own key the same way.

### What's deliberately not built (yet)

- No streaming — the tip arrives as one complete response, which is fine at 2-3 sentences.
- No caching/memoization — every page load re-requests a tip, which is acceptable at demo scale but would need debouncing or caching for production traffic.
- No exponential backoff or delay between fallback attempts within a single request — the chain tries all five models back-to-back as fast as they respond, which is fine since a 429 response is near-instant, not a slow timeout.
