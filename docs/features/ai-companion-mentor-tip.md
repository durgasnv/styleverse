# AI Style Companion — Mentor Tip

## What it does

On the Companion page, alongside the existing rule-based outfit score and recommendations, there's a **Mentor Tip** card: a short, specific styling tip generated by a real LLM call, explaining *why* something works (color theory, silhouette, proportion) rather than just praising the outfit generically.

It reads the actual items on the canvas/look — brand, category, colors — plus the user's selected mood, weather, and skin tone context, and asks the model for 2-3 sentences of concrete, teachable advice.

This replaces what was previously a fully fake/hardcoded "AI" response with a genuine call to an LLM.

## How it's built

### Request flow

1. The Companion page (`artifacts/styleverse/src/pages/companion.tsx`) resolves which look is being reviewed — either a saved look (`?lookId=`) or an unsaved draft passed straight from the Canvas (`?items=<id,id,...>`), which takes priority so "Ask Companion" works without forcing a save first.
2. On load, it fires a `POST /api/companion/mentor-tip` with the resolved items (name, brand, category, colors, occasion tags) plus mood/weather/skin tone, and tracks `mentorTipLoading` / `mentorTipError` / `mentorTip` state for the card.
3. The backend route (`artifacts/api-server/src/routes/companion.ts`) builds a single prompt describing the outfit and context, and calls OpenRouter's chat completions endpoint directly with native `fetch` — no SDK, no queue, just one request/response.
4. The model's reply is returned as `{ tip: string }` and rendered directly in the gradient "Mentor Tip" card.

### Why OpenRouter, and why this model

The route reads `OPENROUTER_API_KEY` from the environment (never written to a file — see [Secrets](#secrets) below) and calls `https://openrouter.ai/api/v1/chat/completions` with:

```
const MENTOR_TIP_MODEL = "google/gemma-4-26b-a4b-it:free";
```

This was chosen empirically. Several popular free-tier models were tried first and returned HTTP 429 ("temporarily rate-limited upstream") under real testing:

- `meta-llama/llama-3.3-70b-instruct:free`
- `meta-llama/llama-3.2-3b-instruct:free`
- `qwen/qwen3-next-80b-a3b-instruct:free`

`google/gemma-4-26b-a4b-it:free` responded reliably in testing and was adopted. If it starts rate-limiting too, swap the constant — it's the only place the model name is referenced.

### Why a hand-rolled route

The rest of the API surface (products, hubs, challenges) is generated from `lib/api-spec/openapi.yaml` via Orval into typed Zod schemas and React Query hooks. This route deliberately skips that pipeline, matching the precedent already set by the voting feature: it's a simple, fast-moving integration where a proxied `fetch` call is enough, and running it through full OpenAPI codegen would add ceremony without real benefit.

### Error handling

The route returns distinct failure modes so the frontend can show a useful message instead of a silent blank card:
- `500` if `OPENROUTER_API_KEY` isn't set at all.
- `400` if the request has no items.
- `502` if OpenRouter's HTTP call fails, or if it responds `200` but with no usable `choices[0].message.content` (e.g. an empty/refused completion).

### Secrets

`OPENROUTER_API_KEY` is passed as an inline environment variable when starting the api-server — it is never written into `.env`, source, or any committed config file. Anyone restarting the server needs to supply it the same way.

### What's deliberately not built (yet)

- No streaming — the tip arrives as one complete response, which is fine at 2-3 sentences.
- No caching/memoization — every page load re-requests a tip, which is acceptable at demo scale but would need debouncing or caching for production traffic.
- No retry-with-fallback-model logic if the configured model starts failing — it just surfaces the `502` to the user.
